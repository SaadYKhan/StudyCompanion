# Study Companion

Private, invite-only study site for two students in Dubai: MK, a Year 12 Edexcel International A Level student (Maths, Physics, Chemistry; SAT; US astrophysics applications) and ZK, a Year 7 student building strong maths and an early path to US universities.

- `site/` is the website (no build step). Cloudflare Workers serves it as static assets, plus a small API in `worker/index.js` for `/api/*` (`wrangler.jsonc`), from the `studycompanion` Worker (https://studycompanion.royalgroup.workers.dev). Once the Worker is connected to this repo (Worker → Settings → Build → Git repository; deploy command `npx wrangler deploy`), every push to `main` redeploys. The `name` in `wrangler.jsonc` must match the Worker's name.
- Sign-in is Cloudflare Access on the whole Worker (emailed one-time code, 7-day sessions). Who may sign in: Zero Trust → Access → Applications → "studycompanion - Cloudflare Workers" → policy "Family". The API re-checks the Access token (`ACCESS_AUD`, `ACCESS_TEAM` in `wrangler.jsonc`) on every call.
- Accounts and data live in the D1 database `studycompanion-db` (schema: `db/schema.sql`). Built for many families: families → students; users (by sign-in email) see a child only through `memberships` (parent = every child in the family; student/tutor = one child). Every change is written to `audit_log`. Email addresses are kept only in the database and Access, never in this repo.
- API (all re-check the Access token and the person's memberships): `GET /api/me`, `GET /api/data`, `GET /api/progress`, `PUT /api/progress/:student/:kind`, `GET /api/family`, `POST /api/family/link`, `POST /api/family/unlink`, and `POST /api/import-legacy` (the one-time copy of the original question log, kept frozen in `worker/legacy.json`). Schema changes go in `db/migrations/`.
- Goals tab (and a summary on the Overview): each child's goals are saved as progress kind `goals` (keys like `a:Physics`: `{kind: 'grade', target: 'A'}` for IAL units, judged against recent Pearson boundaries from `study.js`, June 2022 left out; or `{kind: 'pct', target: 80}`). A meter per subject shows the grade bands and the latest paper; a path chart shows papers so far and the steps to the goal by the exam (one past paper every three weeks; aims, not predictions); "Where the marks are" lists the topics losing the most marks per paper. Papers' `position` is the order the child sat them. Parents and the child can change goals.
- Profile and Roadmap tabs: each child's profile (school system, year group, subjects, interests, applying to/as, target universities with round, deadline and reach/target/likely) is saved as progress kind `profile` (`{a: {...}}`); the year group is stored with the school year it was saved in (`sy`), so it moves up each August by itself. `site/data/pathways.js` holds the generic rules (school systems, US and UK application steps, universities with checked rules, interests and the subjects they need, with sources and a `checked` date; the site flags the rules once they are over 180 days old). The Roadmap builds one card per school year to the final year, with tickable steps (saved as `pathdone`, keys like `a:2026:us:recs`), a subject check against the profile, and university cards. Dated steps are added to Key dates, the countdown and the calendar file; where `study.js` has a date with the same `key`, child and school year (e.g. MK's confirmed SAT and AS dates), that date is used instead. Any other university can be added in the profile with its own deadline.
- Layout: five sections in the top bar (Today, Practice, Progress, Plan, and Family for parents), each with a row of pages, so a child sees at most a handful of choices at once. Children land on **Today**.
- Today: three tasks a day (MK: flashcards, redo two lost questions, a 45-minute focus session; ZK: the daily problem, redo a question, 20 minutes of maths), a progress ring, a streak (a planned rest day, or one missed day in any seven, keeps it), the week as dots, a focus timer that logs itself to the study log, a check-in (sleep, exercise, rest day), the next dates and the next badge. Redone questions come back after a day (not yet or shaky), a week, then a month (got it). Activity is saved per child per day as progress kind `days`; badges (`badges`) are worked out from saved work, so nothing can be gamed by clicking.
- Practice: timed mock papers (MK's go into the past-paper log and the Goals charts; ZK's into his practice log, with personal bests), ZK's daily problem and 10-question quick sets from `site/data/practice.js` (50 original problems, answers checked by script, three hints each), his Key Stage 3 topic map (`skills`), MK's formula sheets, core practicals and Unit 3 skills (saved in `topics`), and a mark-scheme phrase deck in Key notes. The SAT log can take questions missed per content area and shows where the points go.
- Progress: badges, reading log and school reports for both children (`reading`, `reports`). Plan: an applications workspace for the child within a year of applying (`apps`: Common App activities with the 50/100/150-character limits, honours, essay drafts, letters, notes on each university); the tutor gives essay feedback in the same panel and never writes the essay (it reads the saved draft from `apps`).
- Weekly report (parents): days studied, hours against the plan, practice, papers, reading, roadmap steps, badges, goals, sleep and rest, gentle flags, and the next three weeks.
- Reminders: the site is installable (manifest, `site/sw.js`). A device that turns reminders on is stored in D1 (`push_subs`, migration `0004_push.sql`); the Worker makes its own VAPID key pair on first use and keeps it in `app_keys`, and encrypts each message for the device (`worker/push.js`). The browser saves upcoming reminders as progress kind `remind` (a week and a day before deadlines, the day before exams); the 12:07 UTC cron (16:07 in Dubai) sends each child a nudge if nothing is done yet plus that day's reminders, and parents the reminders plus a Sunday summary. No email yet: the account has no domain for sending.
- AI tutor (`worker/chat.js`): "Ask the tutor" on each marked question opens a chat that coaches rather than hands over answers. Each message is limited (on/off per child, daily messages, quiet hours in Dubai time, monthly spend), screened by a small model (study / off-topic / safety; off-topic never reaches the tutor, safety shows helplines and flags the chat), answered by the tutor model with the marked question as context, and the reply is checked before the child sees it. Parents set limits and read every chat on the Family page; chats are deleted after 90 days by the daily cron. Needs `ANTHROPIC_API_KEY` added as type **Secret** (not Text) in Cloudflare → studycompanion → Settings → Variables and Secrets; `keep_vars` in `wrangler.jsonc` stops deploys from removing dashboard variables. Models: `TUTOR_MODEL` (default claude-sonnet-5-5) and `CHECK_MODEL` (default claude-haiku-5-5).
- `tools/test_api.mjs` (needs the `http_ece` package at `HTTP_ECE` or /tmp/ece to check push encryption) runs the Worker locally with a throwaway signing key and checks sign-in, permissions, data, progress, family linking and the tutor chat (with a stand-in for Claude's API) (`WRANGLER=path/to/wrangler node tools/test_api.mjs`). `tools/check_site.py` stands in for the API, so it tests the page without Cloudflare.
- Exam and school dates, term plans, syllabus topics and links live in `site/data/study.js` (application dates and the long-range roadmap now come from each child's profile). To update the site, edit that file and push. Dates are `YYYY-MM-DD`, or `YYYY-MM` when only the month is known; `st: "expected"` marks a date that is not yet published.
- Marked papers and questions live in the database (`papers`, `question_results`), not in this repo; the site loads them from `GET /api/data` after sign-in. `site/data/questions.js` now holds only the shared topic list and mistake types. To add a newly marked paper, insert a `papers` row (next `position`, `source` = 'claude') and its `question_results` rows (fields map to the site's p, q, s, t, also, m, x, w, pr, a, c, e, f), plus an `audit_log` row with `actor_kind` = 'claude'. It shows on the site straight away, with no push.
- Self-test cards for the Key notes tab live in `site/data/cards.js` (one object per card: unit, topic, type, question, answer, and for cards from a marked paper the source question). Never renumber a card's `id`: each student's progress is saved against it. When a new paper is marked, add a `mine` card for each new kind of mistake.
- Progress (Key notes cards, topic ratings, scores, study log, roadmap ticks, redone questions, their own added questions, checklist ticks) is saved per child in the `progress` table via `PUT /api/progress/:student/:kind`, and kept in the browser as a copy. The first time a child's account is opened on a device, anything that browser saved before accounts existed is merged in (a copy is kept under `sc1:backup`). Changes not yet confirmed by the database are kept in the browser (`sc1:dirty`) and retried. The Study log tab still has backup and restore.
- Views: a child sees only their own tabs and work. A parent has a **Viewing** switch: the family view, or exactly what one child sees (changes made there save to that child). Parents also get a **Family** tab to link or remove each child's sign-in email (`/api/family`); the same email must also be added to the Access policy.
- `tools/check_site.py` opens the site in a browser on three different dates, visits every tab and fills in every form; run it before pushing (`python3 tools/check_site.py`). Add `?today=YYYY-MM-DD` to the address to preview the site as of another date.
